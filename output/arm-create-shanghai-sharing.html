01 · Neural rendering

移动端神经渲染：把复杂计算改写成“特征 + 小网络”

用可学习的潜特征承载高频细节，再用小型 MLP 做轻量解码。

  • 目标不是堆一个大模型，而是把模型压进每帧预算。
  • 典型输出：光照、颜色、密度、材质块或可见性。
  • 关键瓶颈：访存、线程调度、GPU 解码与引擎集成。
MagicDawn：AI 渲染在游戏应用中的探索与实践建议 3 分钟

讲稿

这条路线的工程直觉很重要：复杂场景的信息并不一定全部由传统纹理或显式数据保存，可以把一部分信息压成可学习特征，然后由一个很小的网络按需恢复。现场页面给出的 Tiny MLP 规模是 2–8 层、16–128 通道。它足够小，才有机会进入实时渲染；但一旦进入每帧，它的访存、调度和图形 API 支持就与网络精度同样重要。

NDGI

神经动态全局光照：推理不是离线步骤，而是渲染阶段

值得关注的不是“用了 AI”

  • 推理后端、Atlas 纹理、异步提交与同步要一起设计。
  • 按 Tile 分组，避免一次处理整张场景。
  • 最终仍要回到 Shader 和引擎已有资源体系。

工程结论：模型只是管线中的一个阶段，不能孤立优化。

NDGI：Neural Dynamic Global Illumination建议 3–4 分钟

讲稿

这张图是全场很有代表性的一页。神经推理完成后，需要创建或绑定 Atlas、上传 Tile 数据、等待 GPU、把结果复制到物理纹理，再由 Shader 采样。任何一步出现同步等待或资源搬运，模型本身省下来的计算都可能被吃掉。所以端侧 AI 的真正优化单位不是一个算子，而是从数据产生到最终消费的完整链路。

NTC

神经纹理压缩：同时解决包体与运行时访问

50–70% 3A 游戏纹理贴图包体占比（现场页）

传统 BC/ASTC 受通道数量和线性解码能力限制；NTC 利用跨通道、跨 Mip 与空间冗余，把整组 PBR 材质共同编码。

现场方法：可学习潜特征 + MLP；TVLoss 平滑潜空间；Predictive ZIP 进一步压缩 4-bit 残差。
NTC：Neural Texture Compression建议 4 分钟

讲稿

纹理是很适合神经压缩的对象：不同 PBR 通道之间、不同 Mip 层之间以及空间邻域里都有冗余。传统方案通常逐张、逐块处理，无法充分利用这些相关性。现场还特别强调了训练后的潜特征并不天然适合 ZIP，因此先用 TVLoss 约束平滑，再做邻域预测，最后压缩量化残差。这个思路可以抽象成一句话：模型压缩负责“学结构”，传统编码负责“收尾”。

若做 60 分钟版本，可补充现场给出的额外包体收益：BPP 5 为 20.08%，BPP 2.5 为 17.24%，BPP 1.667 为 14.33%。这些是特定测试条件下的结果，不宜脱离上下文推广。

02 · Open-world rendering

把开放世界带到移动端，首先是“一帧如何流动”

移动端优化不是单点降耗，而是让整条帧流水线更短、更并行、更少搬运。

  • 任务图和帧图组织并发工作。
  • 资源准备、命令编码和 IO 都可能成为关键路径。
  • 画质算法必须从一开始就考虑引擎调度。
网易：《燕云十六声》开放世界移动化建议 3–4 分钟

讲稿

开放世界移植不是把 PC 参数整体调低。一个画面从输入到 Present，跨越主线程、游戏线程、计算线程、设备线程和 IO。移动设备更容易受到内存带宽、热设计和调度抖动影响，所以需要把串行阶段拆开、把可以并行的工作前移，并减少 framebuffer 与资源切换。这里和上一部分形成呼应：优化对象始终是端到端链路。

NSS · Neural Super Sampling

NSS 不是只看一张图，而是理解一帧如何到来

每帧输入

低分辨率 Color、Depth、Camera Params

时序信号

Motion Vector、Jitter、SDK 管理的 History

输出

目标分辨率画面

Arm × Unity / 团结引擎建议 4 分钟

讲稿

超分的关键不只是模型看到的当前低分辨率图，还包括深度、相机参数、运动向量、亚像素抖动和历史状态。也就是说，SDK 接入质量会直接决定画质。如果运动向量不准确或历史状态处理不当，就会出现鬼影、闪烁和细节不稳定。对业务团队而言，这说明采购或接入一个算法 SDK 远远不够，还要建立数据契约和质量检查。

Quality / performance trade-off

用更少像素换回接近的观感

0.5 渲染比例

可在此停下来让听众观察细节建议 2–3 分钟

讲稿

这页适合用肉眼比较。NSS 的价值不是把 0.5 神奇变成原生，而是把节省下来的像素预算换给更复杂的材质、光照或更稳定的帧率。评价时应把静态截图、动态稳定性、UI 细节、功耗和时延一起看，而不能只看单张图的 PSNR。

03 · SME2

为什么 SME2 重要：让矩阵计算成为 CPU 的“一等公民”

SME2 面向可伸缩矩阵计算，适合 GEMM、卷积和量化推理等密集工作负载。

  • 不是独立 NPU，也不会自动加速所有算子。
  • 需要识别热点、检查数据类型/形态/布局，再选择 SME2 内核。
  • 正确性优先，同设备、同输入、同线程做 A/B。
硬件能力只有被正确调度，才能形成端到端收益建议 3 分钟

讲稿

这部分最容易产生误解：有了 SME2，并不代表现有应用自动提速。要先找到真正占时的卷积或矩阵算子，再确认数据布局与量化格式是否适合，替换内核并做严格 A/B。现场反复强调 Accuracy First，因为端侧量化和低精度优化很容易在边界输入上产生偏差。

MNN case study

440MB 翻译模型：从“能运行”到“值得在手机运行”

现场方案线索

  • 约 440MB 翻译模型，Hy-MT2-1.8B。
  • 26bit / 1.25bit 等量化探索，配合 Sherry 轻量化。
  • 重点优化 Prefill、Decode 与量化算子。
  • Q2_0C 通过放大分组，降低缩放修正频率，让宽向量单元持续满载。
从指令集突破到多核协同：SME2 在 MNN 引擎中的实践建议 4–5 分钟

讲稿

这项案例把模型、量化格式、内核和产品体验串了起来。小模型只是第一步，真正决定体验的还有首字延迟，也就是 Prefill；以及后续逐 token 生成速度，也就是 Decode。照片中的 Q2_0C 例子体现了底层优化思想：重新组织量化块，让缩放因子的处理频率下降，使 SME2 的宽向量单元更连续地工作。最终产品用翻译 App 做对比，而不是只给算子微基准。

Measured results

现场实测：SME2 对 Prefill 的收益更突出

3.52× Prefill 最高

0.6B：2.80×；4B：3.52×

1.71× Decode 最高

0.6B：1.71×；4B：1.49×

数字来自照片中的特定测试环境，仅用于说明不同阶段的加速差异。

先分阶段测量，再谈总体体验建议 3 分钟

讲稿

为什么 Prefill 加速更明显？Prefill 对整个提示词做并行计算，矩阵计算密度高，更能发挥 SME2；Decode 是逐 token 生成，常受访存、KV Cache 和串行依赖影响。这个差异提醒我们，不能用一个“平均加速比”概括模型体验，应该分别测首字延迟、每 token 延迟、内存、功耗和持续性能。

04 · End-to-end neural image coding

端到端编码的优势，不只是换掉某个模块

从人工设计的预测、变换、量化、熵编码，转向表示—概率模型—重建的协同训练。

  • 压缩目标仍是率失真最优：质量与码率的权衡。
  • 潜力来自端到端联合优化，而非局部模块更“聪明”。
  • 落地时仍需要图执行、数据通路和密集计算调度。
基于 Arm SME2 的端到端图像编解码加速实践建议 3–4 分钟

讲稿

神经图像编码不是把传统编码器里的某个模块换成神经网络，而是围绕质量和码率目标，对表示、概率模型和重建一起训练。这样压缩潜力更高，但工程链路更复杂：图里可能有大量小算子、数据布局转换和中间写回。如果只优化最慢的一个算子，总体性能未必改善。

Pipeline thinking

优化目标从“单算子更快”转向“完整 Pipeline 更短”

1

删掉可证明冗余的转换与复制。

2

融合相邻常规逐元素操作。

3

减少布局变化、中间写回和后端切换。

4

再让真正的密集计算命中 SME2。

这是全场最可迁移的工程方法建议 3–4 分钟

讲稿

这页可以直接迁移到我们自己的性能工作：首先用全链路 Profile 找到真正的等待和搬运；其次做图级清理与融合；然后稳定数据布局与执行边界；最后才替换热点内核。现场底部一句话非常准确：优化目标从“单算子更快”转向“完整 Pipeline 更短”。如果顺序反过来，很容易得到漂亮的微基准，却看不到端到端收益。

我的归纳，不是现场原话建议 4 分钟

讲稿

把这些演讲放在一起，我看到的是一种“系统 AI”范式。第一，模型被做得足够小，成为传统管线的一部分；第二，性能来自异构硬件与数据流协同；第三，所有结果都要回到端到端体验；第四，只有进入引擎、SDK 和系统工具，能力才能被大量开发者使用。这四条比任何单一算法名词更值得带回团队。

Actions for our team

对我们最可执行的三点建议

先画数据流

在优化前画清输入、转换、复制、同步、执行和输出，建立端到端基线。

再找高密度热点

优先选择重复频率高、矩阵密集、输入形态稳定的环节做 AI/SME2 试点。

最后做真实 A/B

同设备、同输入、同线程；同时看质量、延迟、内存、功耗与持续性能。

建议会后输出一个小型验证项目，而不是大规模重构建议 3–4 分钟

讲稿

如果要把大会信息转成行动，我建议从一条真实流水线开始：先做端到端 Profiling 和数据流图；再选一个适合矩阵化、调用频繁而且输入稳定的热点；最后做可复现的 A/B。先证明总体指标改善，再决定是否扩展。不要因为某个硬件指令很新，就先围绕它寻找问题。
