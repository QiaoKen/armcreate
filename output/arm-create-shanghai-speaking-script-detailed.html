开场：我为什么选择这几个主题

大家好。前不久我参加了 Arm Create 上海开发者大会。大会内容很多，现场同时设置了边缘 AI、云 AI 和物理 AI 三个方向。我当天主要关注的是边缘 AI 专场，所以今天的分享不会试图覆盖整场大会，而是聚焦我认为和端侧产品、性能优化以及工程落地最相关的内容。

我把现场看到的内容归纳成五条主线：第一条是移动端神经渲染，包括全局光照、纹理压缩和空间音频；第二条是开放世界游戏如何通过渲染管线和神经超分进入移动端；第三条是 SME2 如何加速端侧大模型推理；第四条是端到端神经图像编码；最后一条是 Windows on Arm 的本地 AI 工具和应用生态。

这些主题表面上差别很大，但我听完以后最大的感受是，它们正在汇合到同一种工程范式：AI 不再只是一个独立功能，而是开始进入每一帧、每一个算子和每一条系统流水线。今天我想重点解释这种变化，以及它对我们的启发。

Topic 1 · 约 3 分钟

核心结论：AI 不再只是“一个功能”

过去我们谈端侧 AI，通常会想到识别、分类、推荐或者对话。它们往往是产品里的一个独立入口：用户触发功能，模型运行，然后返回结果。但是这次大会展示的很多方案不是这种形态。模型被放进了渲染器、编解码器、引擎调度和操作系统工具链，它需要像传统系统组件一样持续、稳定、低成本地工作。

这带来三个明显变化。第一，评价模型不能只看准确率，还要看帧预算、首字延迟、内存带宽、包体、功耗和持续性能。第二，优化对象不再是一个模型或者一个算子，而是数据从产生到消费的完整链路。第三，硬件能力只有进入引擎、SDK、编译器和应用生态以后，才能真正变成用户体验。

所以今天所有案例都可以用一句话串起来：端侧 AI 的竞争重点，正在从“有没有模型”变成“模型能不能成为一个可靠的系统组件”。

Topic 2 · 约 4 分钟

神经渲染：把复杂数据改写成“特征 + 小网络”

【指向图片，从左向右讲】 这张图展示了神经渲染里非常典型的一种结构。系统先根据位置、方向或者材质实例等查询条件，从一个可学习的特征网格中采样。采样结果与其他条件拼接以后，交给一个很小的多层感知机，也就是 Tiny MLP。最后输出颜色、光照、密度、材质块或者可见性等渲染数据。

这里的关键不是使用一个很大的网络，而是把高频、复杂的信息分成两部分：一部分保存在可学习的潜特征里，另一部分由小网络按需解码。现场页面里给出的 Tiny MLP 通常只有两到八层、十六到一百二十八个通道。网络足够小，才有机会在每一帧里运行。

但是进入实时渲染以后，问题就不只是模型推理速度。特征要从哪里读取，线程如何调度，GPU 是否支持对应的矩阵计算，结果怎样回到纹理和 Shader，这些都会影响最终帧时间。所以神经渲染不是“在渲染器旁边加一个 AI 模块”，而是重新设计一部分渲染数据的表达方式。

60 分钟扩展：为什么这种结构适合移动端

移动端的主要约束往往不是单纯算力不足，而是内存带宽、功耗和持续散热。显式保存大量高精度数据会产生存储与读取压力；可学习特征通过更紧凑的表示减少数据量，小网络则用计算恢复细节。当计算成本低于节省下来的带宽成本时，这种交换就可能划算。但它必须在真实设备上测量，不能只根据理论 FLOPS 判断。

Topic 3 · 约 4 分钟

NDGI：模型只是管线中的一个阶段

这张图是我认为现场最有代表性的一页。它描述的是 Neural Dynamic GI，也就是神经动态全局光照的运行时管线。左侧虽然突出显示了 Arm GPU 加速 MLP 解码，但如果顺着箭头看，会发现模型推理只是中间一个步骤。

在推理之前，系统要按 Tile 准备特征和参数，上传数据，创建或者绑定 Atlas 纹理；推理完成后，还要等待 GPU 任务结束，把结果复制到物理纹理，再由 Shader 采样并完成最终画面。任何一次不必要的同步、资源创建或者数据搬运，都可能把神经网络节省下来的时间重新消耗掉。

因此这里最值得记住的不是某个模型结构，而是优化单位发生了变化。我们不能只问 MLP 跑了多少毫秒，而要问从数据准备开始，到最终像素被显示出来，整条链路用了多少时间。端侧 AI 如果不能和引擎已有的资源系统、异步队列与线程模型结合，就很难稳定地进入每一帧。

过渡语：神经网络除了生成光照，也可以用来减少游戏最现实的成本之一——纹理包体。
Topic 4 · 约 5 分钟

神经纹理压缩：模型学习结构，传统编码负责收尾

纹理包体是 3A 游戏移动化时很现实的问题。现场页面提到，纹理贴图可能占整个游戏包体的百分之五十到七十。传统 BC、ASTC 等块压缩格式已经很成熟，但它们通常按固定通道和固定块工作，对现代 PBR 材质中的多通道关联利用有限。

神经纹理压缩的思路，是把一组材质纹理共同编码。比如颜色、法线、粗糙度、金属度和环境遮蔽，它们并不是完全独立的；不同 Mip 层之间也存在信息冗余；相邻空间位置同样高度相关。模型把这些相关性压进共享的潜特征，再由小型 MLP 在运行时恢复需要的通道。

现场还介绍了一个很有意思的改进：训练后的潜特征虽然经过量化，但相邻位置可能跳变很大，直接使用 ZIP 不容易继续压缩。解决办法是用 TVLoss 约束潜空间更加平滑，再进行邻域预测，只保存更小的残差，最后用 ZIP 压缩。也就是说，神经网络负责学习数据结构，传统无损编码负责把剩余冗余进一步压掉。

这个案例的启发是，新旧技术不一定互相替代。最好的系统往往是让学习方法处理传统规则不擅长的部分，再让成熟编码格式完成可逆、稳定和便于部署的最后一步。

空间音频：神经表示也可以描述声场

现场还展示了 Dawn Acoustics 空间音频方案。它可以根据声源和听者的位置、场景几何以及材质信息，推理出动态的声学效果。和传统预烘焙方案相比，它希望减少人工制作成本，并更好地适应开放世界里不断变化的位置和环境。

Topic 6 · 约 4 分钟

开放世界移动化：先理解一帧如何流动

【沿着时间轴从左到右讲】 网易关于《燕云十六声》移动化的分享，首先没有从某个画质开关讲起，而是展示一帧画面如何在多个线程之间流动。主线程处理输入和系统 API；游戏线程执行逻辑、建立 Frame Graph 并触发渲染；计算线程处理任务图、剔除和资源准备；设备线程负责提交与呈现；底部还有文件系统、Shader 编译和其他异步任务。

这张图解释了为什么移动端优化不能简单理解为降低画质。真正影响帧率的可能是线程之间的等待、任务粒度不合理、资源准备太晚、命令编码集中在关键路径，或者 IO 和 Shader 编译产生抖动。单个模块快一点，不代表下一帧能更早到来。

所以开放世界移动化的核心，是让整条帧流水线更短、更并行、更少搬运。任务图和帧图用来组织依赖，异步任务尽量提前，资源布局和 Render Pass 则要减少切换。这和前面 NDGI 的结论完全一致：性能优化的对象是完整链路，不是孤立函数。

过渡语：当基础流水线稳定以后，神经超分就可以帮助我们用更少的像素预算换回接近的画质。
Topic 7 · 约 4 分钟

NSS：它不只看一张图，还要理解这一帧如何到来

NSS 是 Neural Super Sampling，也就是神经超分采样。很多人第一次接触超分，会把它理解成把一张低分辨率图片放大。但是游戏里的实时超分不是单张图片处理，而是时序重建。

从这张图可以看到，每一帧都要提供低分辨率颜色、深度和相机参数；同时还需要运动向量和亚像素抖动；SDK 自己还会维护历史状态。模型结合当前帧和历史信息，输出目标分辨率画面。换句话说，NSS 的效果不仅取决于模型，也取决于引擎持续提供的信息是否准确。

如果运动向量不正确，物体边缘可能出现拖影；如果历史状态在镜头切换后没有及时清理，可能出现残留；如果透明物体、粒子和 UI 的处理顺序不合理，也会出现闪烁或细节丢失。所以接入一个神经超分 SDK，不是完成一次 API 调用，而是建立一套稳定的数据契约和质量检查流程。

画质与性能：把节省的像素预算用到更重要的地方

【停顿三秒，让听众观察】 左侧是渲染比例零点七的 SMAA，右侧是渲染比例零点五的 NSS。现场给出的结论是，NSS 只渲染一半分辨率，实际渲染面积更小，但在这组旷野场景中，观感与零点七比例的 SMAA 接近。

这里的价值不是证明零点五永远等于原生画质，而是说明我们可以重新分配 GPU 预算。减少基础像素数量以后，节省下来的预算可以用于更复杂的光照、材质、植被，也可以用于提高帧率或者降低功耗。

评估时也不能只看一张静态截图。真正的产品验证要同时看动态稳定性、快速移动时的鬼影、UI 和细线条、输入时延、功耗以及长时间运行后的频率变化。画质是一种端到端体验，而不是单一指标。

Topic 9 · 约 4 分钟

SME2：让矩阵计算成为 CPU 的一等公民

SME2 可以理解为 Arm 面向可伸缩矩阵计算的一组架构扩展。它适合矩阵乘、卷积以及量化推理中的密集计算。对端侧 AI 来说，它的意义是 CPU 不再只承担控制和轻量逻辑，也可以更高效地处理一部分矩阵工作负载。

但是现场特别强调，SME2 不是一块独立 NPU，也不会自动加速所有算子。正确的路径是先识别计算热点，确认它确实是卷积或者矩阵类任务；然后检查数据类型、张量形态和内存布局是否适合；再调度 SME2 优化内核；最后验证输出一致性，并在同一设备、同一输入、同一线程条件下做 A/B。

这个顺序很重要。低精度量化和硬件特化可能在边界输入上产生误差，所以必须 Accuracy First。并且即使单个内核很快，如果前后发生大量布局转换或者后端切换，端到端性能也不一定提高。

Topic 10 · 约 5 分钟

MNN 案例：从“手机能跑”到“手机值得跑”

这项分享展示了一个大约四百四十兆的端侧翻译模型。现场材料里可以看到 Hy-MT2-1.8B、低比特量化、Sherry 轻量化，以及针对 Prefill 和 Decode 的优化。这里最有价值的，不是模型文件做到了多少兆，而是他们把模型、量化格式、底层算子和手机端产品体验连在了一起。

对于生成式模型，用户体验至少包含两个阶段。第一个阶段是 Prefill，也就是模型处理完整提示词并生成第一个 token 之前的计算，它直接影响首字等待时间。第二个阶段是 Decode，也就是后续逐 token 生成，它决定输出是否流畅。这两个阶段的计算特征不同，所以优化效果也不同。

现场还展示了 Q2_0C 量化算子的思路。普通 GGUF 格式把三十二个元素作为一块并携带缩放因子；Q2_0C 把分组放大到五百一十二个元素共享一个缩放因子，从而降低缩放修正频率，让 SME2 的宽向量计算单元更持续地保持满载。这里本质上是在为硬件重排数据，而不是只替换一条指令。

最终他们没有停在算子 benchmark，而是用翻译 App 展示支持 SME2 和不支持 SME2 的真实差别。这一点很重要：端侧优化只有回到真实交互，才能证明它值得投入。

Topic 11 · 约 4 分钟

性能数字：先分阶段测量，再谈总体体验

【先说明测试条件】 这组数据是在 Mac mini M4 上，对 Qwen3 零点六 B 和四 B 模型进行四比特量化测试。上下文长度是一千零二十四，使用单线程。现场把 SME2 与 Arm V8.6 路径进行了对比。

在 Prefill 阶段，零点六 B 模型从每秒二百六十点一 token 提升到七百二十七点八，约为二点八倍；四 B 模型从三十八点三提升到一百三十四点九，达到三点五二倍。在 Decode 阶段，零点六 B 模型约为一点七一倍，四 B 模型约为一点四九倍。

为什么 Prefill 收益更大？因为 Prefill 会对整段提示词做大量并行矩阵计算，计算密度更高，更容易发挥 SME2。Decode 是逐 token 生成，串行依赖更强，还会受到 KV Cache、访存和调度开销影响。因此同一套硬件扩展，在模型不同阶段的收益并不相同。

所以在我们自己的测试里，不应该只给一个平均加速比。至少要分别报告首字延迟、每 token 延迟、峰值内存、功耗和持续运行后的性能。只有这样，数据才能对应真实体验。

过渡语：SME2 不只服务大模型推理，它同样可以进入图像编解码这样的传统基础设施。
Topic 12 · 约 4 分钟

端到端神经图像编码：不是替换模块，而是联合优化目标

传统图像编码由人工设计的一系列模块组成，包括预测、变换、量化和熵编码。每个模块都非常成熟，标准和硬件生态也很完整。端到端神经图像编码则把表示学习、概率模型和重建放到同一个训练目标里，直接围绕质量与码率的权衡进行优化。

现场用 D 加 Lambda 乘 R 来表示率失真目标。D 是失真，也就是画质损失；R 是码率；Lambda 控制二者之间的权衡。端到端训练的潜力在于，系统可以跨越原来人为划分的模块边界，共同寻找更合适的表示。

但是工程上它也更复杂。计算图中可能存在大量小算子、类型转换、数据复制和中间张量写回。如果只把某个卷积替换成 SME2 内核，而其他部分仍然频繁搬运数据，总体速度可能没有明显变化。所以这个案例最终又回到了同一个主题：端到端模型需要端到端系统优化。

Topic 13 · 约 5 分钟

Pipeline 优化：单算子更快，不等于应用更快

这张图给出了非常清晰的优化顺序。第一步，清理可以证明冗余的转换和复制。第二步，把相邻的常规逐元素操作进行算子融合。第三步，减少布局变化、中间写回以及不同后端之间的切换。完成这些工作以后，再让真正的卷积和矩阵热点进入 SME2 路径。

为什么要按这个顺序？假设计算 A 和计算 B 本身都很快，但中间必须做一次类型转换、复制数据、调整布局，然后再写回内存，那么完整链路仍然很慢。如果我们只把计算 A 优化两倍，用户可能几乎感受不到。只有把 A 和 B 融合，让数据连续流动，才能真正缩短 Pipeline。

这也给我们的性能工作提供了一个通用模板。先用全链路 Profile 找到时间花在哪里；再画出数据流，识别转换、复制和同步；然后进行图级清理与融合；最后才针对稳定的热点选择硬件特化内核。优化完成后，还要回到真实输入做端到端 A/B。

我认为这比记住某个 SME2 指令更重要。硬件会更新，但“完整 Pipeline 更短”会一直是有效的目标。

五场演讲背后的四条共同规律

把这些案例放在一起，我归纳出四条共同规律。

第一是 AI 小型化。现场真正进入实时系统的，往往不是一个庞大的通用模型，而是可学习特征加小型解码器，或者经过深度量化和特化的端侧模型。模型需要足够小，才能成为流水线的一部分。

第二是异构协同。CPU、GPU、NPU、内存系统、图形 API 和编译器共同决定结果。我们不能只根据 TOPS 或 FLOPS 判断体验，也不能默认某个硬件后端适合所有算子。

第三是端到端测量。图形要同时看画质、帧时间、功耗和包体；大模型要分别看 Prefill 和 Decode；编解码要同时看质量、码率和整个图执行时间。指标必须对应用户实际等待和设备实际消耗。

第四是生态优先。只有当能力进入引擎、SDK、工具链和应用兼容体系，普通开发者才可能稳定使用。算法首秀代表可行性，工具链和生态才代表规模化。

这四条可以合并成一个词：系统 AI。它不是把模型附加到系统上，而是让模型与数据流、硬件和软件生命周期一起设计。

Topic 16 · 约 4 分钟

对团队的建议：从一条真实流水线开始

第一，先画数据流。选择一个真实业务场景，把输入、格式转换、复制、同步、执行和输出全部画出来，并建立端到端性能基线。没有这张图，我们很容易优化到错误的位置。

第二，再寻找高密度热点。优先考虑调用频率高、矩阵计算密集、输入形态稳定，并且结果容易验证的环节。它可能适合 SME2、GPU Compute 或者一个小型神经模块，但选择应来自 Profile，而不是来自对新技术的偏好。

第三，做真实 A/B。保持同一设备、同一输入、同一线程和相同温度条件，除了平均延迟，还要记录长尾、内存、功耗和持续运行后的变化；涉及图像和音频时，还要准备可重复的质量评估。

我的建议不是立刻进行大规模重构，而是做一个小型验证项目。先证明完整 Pipeline 的总体指标确实改善，再决定是否扩大投入。这样既能吸收大会的新技术，也能控制工程风险。

可用于讨论的三个问题

一，我们的产品里哪条高频流水线最适合第一个试点？二，当前最大的成本是计算、带宽、复制、同步，还是工具链？三，如果性能提高百分之三十，我们愿意接受多大的质量、功耗或维护成本？
